# Website preview for Umbraco drafts

Date: 2026-10-30
Status: approved design, pending implementation plan

## Problem

"Save and preview" in the Umbraco backoffice opens Umbraco's built-in preview, which renders Razor templates. The CMS
is headless and has no templates (`HeadlessComposer` blocks and strips them), so preview shows nothing. Editors have
no way to see a draft before publishing.

## Goal

An editor saves a draft, picks **Preview on website** from the Save and preview menu, and sees that draft rendered by
the real Astro site, while the public site keeps showing the published version.

Success criteria:

- The draft (unpublished changes, including never-published pages) renders with the same components as the live page.
- Only signed-in staff can see drafts. Anonymous visitors get no draft content from the web or the API.
- Preview responses are never stored by web-cache or any shared cache.
- Core code still works with an empty CMS, and with staff sign-in turned off (preview is then unavailable, not broken).

## Decisions

- **Access:** the web's existing staff session (`staff_session`, Keycloak `staff` realm locally, Entra ID in
  production). Editors who signed into the backoffice through the staff realm get single sign-on. Signed preview
  links for external reviewers are out of scope.
- **API surface:** a dedicated preview endpoint guarded by a shared key only the web holds. The published endpoints
  stay unchanged. Rejected: a `?preview=` flag on `/api/content` (public endpoints would branch on auth and risk
  caching drafts), and the web calling Umbraco directly (breaks adapter neutrality).
- **Entry point:** an extra `previewOption` in the Save and preview dropdown. The default button keeps Umbraco's
  built-in preview.

## Design

### Flow

```
Backoffice "Preview on website"
  → GET {web}/preview/{documentKey}?culture=…           (Umbraco IUrlProvider "website")
  → web: staff session? no → 302 /auth/staff/login?returnTo=/preview/{key}…
  → web → API: GET /api/preview/content/{key}  X-Preview-Key: …
  → API → Umbraco Delivery API: GET /item/{key}  Preview: true  Api-Key: …
  ← Page (same contract as /api/content), Cache-Control: no-store all the way back
```

### CMS (`src/Cms`)

- `Headless/WebsitePreviewUrlProvider.cs`: `IUrlProvider` with `Alias = "website"`. `GetPreviewUrlAsync(content,
  culture, segment)` returns `UrlInfo.AsUrl("{Preview:WebUrl}/preview/{content.Key}" + "?culture=" when culture is set,
  provider "website")`. `GetUrl` returns `null` and `GetOtherUrls` returns nothing, so published URL generation is
  untouched. When `Preview:WebUrl` is not set, it returns no preview URL.
- Registered in `HeadlessComposer` (`builder.UrlProviders().Append<WebsitePreviewUrlProvider>()`).
- `wwwroot/App_Plugins/WebsitePreview/umbraco-package.json`: a `workspaceActionMenuItem` of `kind: "previewOption"`
  for `Umb.WorkspaceAction.Document.SaveAndPreview`, `meta: { label: "Preview on website", icon: "icon-globe",
  urlProviderAlias: "website" }`. No build step, same as `App_Plugins/ProductPicker`.
- `apphost.cs`: `Preview__WebUrl` on `cms` = the web-cache endpoint (the URL editors normally browse). Azure: the web
  container app's URL in `containerapps.tf`.

### API (`src/Api`)

- `IContentSource.GetPreviewByIdAsync(string id, string? culture, CancellationToken ct)` → `Page?`.
- `UmbracoContentSource`: same request as `GetByIdAsync` (`/item/{id}`) plus the `Preview: true` header, mapped with
  `DeliveryApiMapper`. The Delivery API key the API already sends grants preview access. No other Umbraco knowledge
  leaves the adapter.
- `Endpoints/PreviewEndpoints.cs`: `GET /api/preview/content/{id}` (`GetPreviewContentById`, tag `Preview`):
  - `X-Preview-Key` is compared with `Preview:ApiKey` using `CryptographicOperations.FixedTimeEquals` on UTF-8 bytes.
    Missing or wrong key → 401. No configured key → 404 (feature off).
  - Draft not found → 404. Otherwise 200 with the `Page` contract.
  - Every response has `Cache-Control: no-store`.
- `PreviewOptions` (`Preview:ApiKey`), same options pattern as the existing sections.
- OpenAPI document regenerated by the build (`src/Api/openapi/Api.json`).

### Web (`src/Web`)

- `components/PageView.astro`: the body of `pages/[...slug].astro` (layout, article or blog post view, hero-less
  header, `BlockList`) moved here unchanged and used by both routes. No copy of the rendering.
- `pages/preview/[id].astro`:
  - Staff sign-in off → 404 page.
  - No staff session → 302 to `/auth/staff/login?returnTo=<this path and query>`.
  - Otherwise it calls the API with `X-Preview-Key: PREVIEW_API_KEY` (server-side env, never sent to the browser),
    passing `culture`. 404 → NotFound view. 401 or any other error → throw (logged by `500.astro`; it means the web
    is misconfigured).
  - Renders `PageView` with a visible "Preview: unpublished draft" banner, `<meta name="robots" content="noindex">`,
    and `Cache-Control: no-store` (the middleware keeps an existing `Cache-Control`).
- `lib/api/client.ts`: a small `previewPage(id, culture)` helper that adds the header, so the key stays in one place.
- `npm run gen:api` regenerates `schema.d.ts`.

### Secrets and infrastructure

- New Aspire parameter `preview-api-key` (32 random alphanumeric characters): `GeneratedSecret("preview-api-key")` in
  `apphost.cs`, passed as `Preview__ApiKey` to `api` and `PREVIEW_API_KEY` to `web`.
- `scripts/init-secrets.sh`: add the key (set only when missing, like the others).
- Terraform: `random_password.preview_api_key` and a Key Vault secret in `keyvault.tf`; secret references for the api
  and web container apps in `containerapps.tf`; `Preview__WebUrl` for the cms container app.
- Rotation: just restart (the web and API read it on start).

### Caching and security

- `no-store` on the API and web responses means web-cache never stores a draft. The per-visitor staff session
  decides access, which matches the AGENTS.md rule that per-visitor state stays out of cached pages.
- Drafts never reach the public `/api/content` endpoints or the search index.
- The preview key is only accepted on `/api/preview/*`. It does not unlock anything else.

## Testing

- `tests/Api.Tests/PreviewEndpointsTests.cs`: missing key → 401, wrong key → 401, no configured key → 404, valid key
  → 200 with `Page` and `Cache-Control: no-store`, unknown id → 404 (fake `IContentSource`).
- `UmbracoContentSourceTests`: `GetPreviewByIdAsync` sends `Preview: true` to `/item/{id}` and maps the fixture;
  `GetByIdAsync` still does not send it.
- `dotnet build AspireTest.slnx && dotnet test AspireTest.slnx`, `npm run check`, `terraform fmt -check`.
- Manual check on the running stack: edit an article's title without publishing → Preview on website → signed-in
  staff see the new title with the banner; the public URL still shows the old title; an anonymous browser on
  `/preview/{key}` is redirected to sign-in; `curl` to `/api/preview/content/{key}` without the key gets 401.

## Out of scope

- Signed preview links for reviewers without a staff account.
- Preview of Drupal products.
- Lists inside a draft page (latest articles, blog list, navigation) still show published content.
- Replacing the default Save and preview button.
- Live refresh of the preview tab on save.
